Behavior-Driven Development: 행위 주도 개발의 원리와 적용

Methodology Series Vol.2

Abstract

행위 주도 개발(Behavior-Driven Development, BDD)은 TDD(Test-Driven Development)에서 발전한 소프트웨어 개발 방법론으로, 비즈니스 이해관계자와 개발자 간의 협업을 통해 시스템의 기대 동작을 자연어에 가까운 형식으로 정의한다. 본 논문에서는 BDD의 핵심 원리인 Given-When-Then 패턴과 유비쿼터스 언어(Ubiquitous Language)의 개념을 분석하고, Cucumber, SpecFlow 등의 도구를 활용한 실제 적용 방법을 제시한다. BDD는 요구사항의 명확한 문서화, 개발과 비즈니스 간의 소통 개선, 인수 테스트 자동화를 통해 소프트웨어 품질 향상에 기여한다.

Keywords: Behavior-Driven Development, BDD, Gherkin, Cucumber, Given-When-Then, Acceptance Testing

1. Introduction

2003년 Dan North는 TDD를 가르치면서 발견한 문제점들을 해결하기 위해 BDD 개념을 제안했다. TDD에서 개발자들이 겪는 주요 혼란—무엇을 테스트해야 하는가, 어디서부터 시작해야 하는가, 얼마나 테스트해야 하는가—에 대한 해답으로 BDD가 탄생했다.

BDD is about implementing an application by describing its behavior from the perspective of its stakeholders.

— Dan North, BDD 창시자

BDD의 핵심 아이디어는 테스트를 "테스트"가 아닌 "행위 명세(Behavior Specification)"로 재정의하는 것이다. 이를 통해 기술 팀과 비즈니스 팀 모두가 이해할 수 있는 공통 언어로 시스템의 기대 동작을 기술할 수 있게 된다.

2. Three Amigos Collaboration

BDD는 "Three Amigos" 미팅을 통해 다양한 관점을 통합한다. 이 세 역할이 함께 요구사항을 분석하고 시나리오를 작성한다:

Business

Business (PO/BA)

비즈니스 가치와 요구사항 관점. "왜 이 기능이 필요한가?"를 설명

Dev

Developer

기술적 구현 관점. "어떻게 구현할 것인가?"를 고려

QA

Tester (QA)

품질과 엣지 케이스 관점. "무엇이 잘못될 수 있는가?"를 탐색

3. Given-When-Then Pattern

3.1 패턴의 구조

BDD 시나리오는 Given-When-Then 패턴을 사용하여 구조화된다. 이 패턴은 Arrange-Act-Assert(AAA) 패턴과 유사하지만, 비즈니스 관점에서 더 자연스럽게 읽힌다.

Given 사전 조건 / 초기 컨텍스트 설정
시스템이 특정 상태에 있음을 명시
When 행위 / 이벤트 발생
사용자 또는 시스템이 수행하는 액션
Then 기대 결과 / 결과 검증
행위 후 시스템의 예상 상태

3.2 Gherkin 문법 예시

Gherkin은 BDD 시나리오를 작성하기 위한 비즈니스 가독성이 높은 DSL(Domain-Specific Language)이다:

Feature: 사용자 로그인 # 사용자가 시스템에 안전하게 접근할 수 있도록 Scenario: 유효한 자격 증명으로 로그인 Given 사용자가 로그인 페이지에 있다 And 등록된 계정 "user@example.com"이 존재한다 When 이메일에 "user@example.com"을 입력한다 And 비밀번호에 "password123"을 입력한다 And 로그인 버튼을 클릭한다 Then 대시보드 페이지로 이동해야 한다 And 환영 메시지가 표시되어야 한다 Scenario: 잘못된 비밀번호로 로그인 시도 Given 사용자가 로그인 페이지에 있다 When 이메일에 "user@example.com"을 입력한다 And 비밀번호에 "wrongpassword"를 입력한다 And 로그인 버튼을 클릭한다 Then 오류 메시지 "잘못된 자격 증명"이 표시되어야 한다

6. BDD Workflow

Discovery
→
Formulation
→
Automation
→
Execution

Figure 1. BDD Implementation Workflow

BDD 워크플로우는 네 단계로 구성된다:

  • Discovery: Three Amigos 미팅을 통해 요구사항 탐색 및 예제 도출
  • Formulation: 도출된 예제를 Gherkin 시나리오로 문서화
  • Automation: Step Definition 코드를 작성하여 시나리오 자동화
  • Execution: 자동화된 테스트 실행 및 결과 검증

7. Benefits of BDD

협업 향상

비즈니스와 기술 팀 간의 공통 언어로 소통 장벽 해소

살아있는 문서

실행 가능한 명세서가 항상 최신 상태의 문서 역할

명확한 요구사항

구체적인 예제를 통해 모호한 요구사항을 명확히 정의

회귀 테스트

자동화된 인수 테스트로 기능 회귀 방지

사용자 중심

사용자 스토리 기반 개발로 실제 가치 전달에 집중

설계 개선

Outside-In 개발 방식으로 더 나은 API 설계 유도

8. Conclusion

Behavior-Driven Development는 TDD의 기술적 실천을 비즈니스 가치 중심으로 확장한 개발 방법론이다. Given-When-Then 패턴과 유비쿼터스 언어의 사용은 이해관계자 간의 소통을 원활하게 하고, 요구사항을 실행 가능한 명세로 변환한다.

BDD의 성공적인 도입을 위해서는 도구의 선택보다 협업 문화의 정착이 더 중요하다. Three Amigos 미팅을 통한 지속적인 대화와 Example Mapping 등의 기법을 활용하여 모든 이해관계자가 시스템의 기대 동작에 대해 동일한 이해를 갖도록 해야 한다.
