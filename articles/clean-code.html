Clean Code: 클린 코드 원칙과 실천

Methodology Series Vol.3

클린 코드는 읽기 쉽고, 이해하기 쉽고, 변경하기 쉬운 코드를 작성하기 위한 원칙과 실천의 집합이다. Robert C. Martin(Uncle Bob)의 저서 "Clean Code"를 중심으로, 본 논문에서는 의미 있는 네이밍, 함수 설계, SOLID 원칙, 코드 스멜 등 클린 코드의 핵심 개념을 분석한다. 클린 코드는 단기적으로 시간이 더 걸릴 수 있으나, 장기적으로 유지보수 비용을 크게 절감하고 소프트웨어의 수명을 연장한다.
Keywords: Clean Code, SOLID Principles, Code Smell, Refactoring, Naming, Software Craftsmanship

1. Introduction

코드는 쓰는 시간보다 읽는 시간이 10배 이상 많다. 따라서 읽기 쉬운 코드를 작성하는 것은 개발 생산성에 직접적인 영향을 미친다. 클린 코드는 "작동하는 코드"를 넘어 "유지보수 가능한 코드"를 목표로 한다.

Clean code is simple and direct. Clean code reads like well-written prose.

— Grady Booch

Any fool can write code that a computer can understand. Good programmers write code that humans can understand.

— Martin Fowler

2. Meaningful Names

좋은 이름은 코드의 의도를 명확히 드러낸다:

  • 의도를 분명히: int d; (나쁨) → int elapsedDays; (좋음)
  • 발음 가능한 이름: genymdhms (나쁨) → generationTimestamp (좋음)
  • 검색 가능한 이름: 7 (나쁨) → WORK_DAYS_PER_WEEK (좋음)
  • 클래스명은 명사: Customer, Account (좋음)
  • 메서드명은 동사: getData(), setName() (좋음)

3. Functions

함수 작성 규칙:

  • 작게 만들어라: 함수는 20줄 이내가 이상적
  • 한 가지만 해라: 함수는 하나의 작업만 수행 (Single Responsibility)
  • 함수 당 추상화 수준은 하나로: 한 함수 내에 추상화 수준을 섞지 마라
  • 서술적 이름 사용: 함수 이름만으로 무엇을 하는지 알 수 있어야
  • 인수는 적게: 이상적으로는 0개, 최대 3개까지
  • 부수 효과 없애기: 함수 이름에 드러나지 않은 동작은 하지 마라

4. SOLID Principles

Single Responsibility

클래스는 하나의 변경 이유만 가져야 한다

Open-Closed

확장에 열려있고 수정에 닫혀있어야 한다

Liskov Substitution

하위 타입은 상위 타입을 대체할 수 있어야 한다

Interface Segregation

클라이언트별 인터페이스를 분리하라

Dependency Inversion

추상화에 의존하라, 구체화에 의존하지 마라

5. Code Smells

  • Duplicated Code: 동일하거나 유사한 코드가 여러 곳에 존재. DRY 원칙 위반
  • Long Method: 너무 긴 메서드. 하나 이상의 책임을 가질 가능성 높음
  • Large Class: 너무 많은 인스턴스 변수와 메서드를 가진 클래스
  • Long Parameter List: 3개 이상의 파라미터. 객체로 묶는 것을 고려
  • Divergent Change: 하나의 클래스가 여러 이유로 자주 변경됨
  • Feature Envy: 메서드가 자신의 클래스보다 다른 클래스의 데이터를 더 많이 사용

6. Comments

좋은 주석: 법적 주석, TODO 주석, 의도 설명, 경고, API 문서(Javadoc). 단, 코드로 설명할 수 있다면 주석을 쓰지 마라.

나쁜 주석: 주절거리는 주석, 중복 주석, 닫는 괄호 주석, 주석 처리된 코드, 이력 주석, 있으나마나 한 주석.

7. Best Practices

DRY

Don't Repeat Yourself. 모든 지식은 시스템 내에서 단일하고 명확하게 표현

KISS

Keep It Simple, Stupid. 불필요한 복잡성을 피하고 단순하게 유지

YAGNI

You Aren't Gonna Need It. 필요할 때까지 기능을 추가하지 마라

Fail Fast

오류는 가능한 빨리 발견하고 보고하라. 숨기지 마라

Boy Scout Rule

"캠프장은 처음 왔을 때보다 깨끗이 하고 떠나라". 코드도 마찬가지

Composition over Inheritance

상속보다 합성을 선호하라. 더 유연하고 덜 결합된 설계

8. Error Handling

  • 예외 사용: 오류 코드 반환 대신 예외를 사용하라
  • 의미 있는 예외: 예외에 충분한 컨텍스트를 제공하라
  • null 반환 금지: null을 반환하거나 전달하지 마라. Optional, 빈 컬렉션, 특수 케이스 패턴을 사용

9. Conclusion

클린 코드는 단순히 "작동하는 코드"를 넘어 "읽기 좋은 코드", "변경하기 쉬운 코드"를 목표로 한다. 의미 있는 네이밍, 작고 명확한 함수, SOLID 원칙 준수는 클린 코드의 핵심 요소이다.

클린 코드 작성은 기술적 역량뿐 아니라 장인 정신(Software Craftsmanship)을 요구한다. 지속적인 학습과 연습, 그리고 코드 리뷰를 통한 피드백이 클린 코드 역량을 향상시킨다. 기술 부채를 줄이고 장기적인 소프트웨어 품질을 확보하기 위해 클린 코드는 필수적이다.
